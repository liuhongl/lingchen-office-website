# 灵宸研究院文章转换 V2 规则

## 1. 目标与适用范围

本规范用于将“灵宸研究院模块的内容”压缩包中的 DOCX 文章转为官网可索引详情页。

V2 的核心目标是：

1. 文字、标点、数字、空格、段落顺序、图注和表格内容零增删改。
2. 图片使用 DOCX 内原始 media，不截图、不重绘、不插值放大。
3. 段落级布局属性从 DOCX XML 逐段提取，不用统一 CSS 猜测。
4. 只保留经用户确认的官网化例外，其他差异均以 DOCX 为准。
5. 内容、视觉、SEO/GEO 和工程验证分别过门，不相互替代。

## 2. 事实来源与冲突顺序

| 优先级 | 事实来源 | 控制内容 |
|---:|---|---|
| 1 | 用户在当前会话明确确认的覆盖 | 官网宽度、分页、可见展示例外 |
| 2 | 单篇原始 DOCX | 详情页文字、结构、图片、表格、行内与段落属性 |
| 3 | MasterGo 指定文章设计 | 公共详情外壳和已明确的列表卡片 |
| 4 | 冻结的官网公共组件 | Header、Footer、Logo、BookingModal |
| 5 | 现有代码 | 只作实现参考，不反向覆盖上述事实 |

无法消解的冲突必须停止对应文章，不得自行选一个“更好看”的方案。

## 3. 已确认的官网化例外

以下项目不复制 Word 的物理纸张，是用户已确认的正式例外：

- 桌面内容宽度使用公共 Header 的 `1180px` 网格。
- 不保留 A4 分页、页眉、页脚和纸张边距，页面高度由内容驱动。
- 公共 Header/Footer 直接复用，文章只控制研究院导航高亮。
- 详情页主标题和副标题作为一组居中。
- 标题区与摘要之间使用 40px 纯白留白，无横向分隔线。
- 页面头部和正文画布使用纯白背景。
- 摘要属于官网统一组件：参考前两篇已发布文章，固定使用 `#F4F6FA` 背景、3px `#2E5FA3` 左边框、11pt 字号与 1.416667 行高；标签为 `#1F4E79` 加粗，正文为 `#0F172A`。容器使用上/下 18px、右 22px、左 18.6667px 内边距，上 8px、下 13.3333px 外边距。2026-07-21 曾短暂尝试顶部内边距 0，用户随即撤销，不得作为后续规则使用。
- 关键词属于官网统一组件：10.5pt、1.333333 行高、段后 13.3333px、无背景/边框/缩进；网页标签统一展示为 `关键词｜`，使用 `#1F4E79` 加粗，后续正文统一 `#595959`。
- 源 DOCX 和正式 JSON 必须保留原始关键词标签，供内容深比较使用；如果源文为 `关键词：`，仅渲染层按用户确认覆盖显示为 `关键词｜`。标签后的关键词正文仍严格保留原文。
- 源 DOCX 将“摘要”标签和摘要正文拆成相邻两个段落时，JSON 使用独立 `leadLabel` 保存标签、`text` 保存正文；网页允许把两者放入同一个统一摘要容器，但不得补写源文件不存在的分隔符。
- 只有独立关键词字段才应用统一关键词组件；普通正文中的“关键词包括……”保持所在段落完整，不拆分、不改成 `关键词｜`。
- 行动/落地建议继续保留各篇 DOCX 的底纹和左边框，同时补充 18px 上下、22px 右侧内边距；左侧继承 DOCX 缩进与边框间距。
- 移动端不作为正式视觉验收项；只保证不破坏桌面、页面可打开且无根级溢出。

新的例外必须在对应 `scope.md` 中记录用户原话、日期、原状态和覆盖值。

## 4. 输入文件与命名

每篇开工前必须登记：

- DOCX 绝对路径与原始文件名。
- DOCX SHA-256；后续每次重提取均必须匹配。
- 文章分类、稳定 slug、`sourceTitle`、`displayTitle`和日期状态。
- 原始非空文本段落数、图片数、表格数和表格行列。

slug 使用稳定的英文小写路径，发布后不因标题微调而变更。

## 5. 内容零改动规则

### 5.1 文本

- 必须保留所有标点、数字、单位、英文大小写、英文空格和括号形式。
- 不纠错、不润色、不改写摘要、不为 SEO 扩写正文。
- `segments` 拼接后必须逐字符等于该 block 的 `text`。
- 渲染后的文本节点必须与结构化数据再比较一次，不只检查源码。

### 5.2 内容块顺序

- DOCX 主文档 XML 中的段落、图片容器和数据表顺序即为页面顺序。
- 不允许把图片移到章节顶部、把表格拆成卡片或把结论提到首屏。
- 不保留空白 A4 分页，但不得因去分页而合并相邻段落。

## 6. DOCX 行内格式映射

每个非空 run 至少可提取：

| DOCX 属性 | JSON | 渲染规则 |
|---|---|---|
| 原文 | `segments[].text` | 原样输出 |
| 加粗 | `segments[].bold` | `<strong>` |
| 斜体 | `segments[].italic` | `<em>` |
| 下划线 | `segments[].underline` | `<u>` |
| 直接字色 | `segments[].color` | 只在 DOCX 明确设置时输出 |
| 直接字号 | `segments[].fontSizePt` | 以 `pt` 输出，不四舍五入为整像素 |

字体名称未取得可靠的网页字体文件时，继续使用官网冻结字体栈，不宣称字体像素级一致。

## 7. DOCX 段落格式映射

`layout` 对象必须保存 DOCX 直接段落属性，不推断不存在的值：

| DOCX XML | JSON | CSS 映射 |
|---|---|---|
| `w:spacing/@w:before` | `spaceBeforeTwips` | `margin-top = twips / 15 px` |
| `w:spacing/@w:after` | `spaceAfterTwips` | `margin-bottom = twips / 15 px` |
| `w:spacing/@w:line` + `auto` | `lineTwips` / `lineRule` | `line-height = lineTwips / 240` |
| `w:ind/@w:firstLine` | `firstLineTwips` | `text-indent = twips / 15 px` |
| `w:ind/@w:left` | `leftTwips` | `padding-left = twips / 15 px` |
| `w:jc/@w:val` | `alignment` | `both → justify`、`center → center` |
| `w:shd/@w:fill` | `backgroundColor` | 原色值背景 |
| `w:pBdr/w:left` | `leftBorder` | 颜色、八分之一磅粗细和边框间距分别换算 |
| `w:pBdr/w:bottom` | `bottomBorder` | 颜色、八分之一磅粗细和边框间距分别换算 |
| 段落所有非空 run 同字号 | `fontSizePt` | 段落默认字号 |

规则：

- 类型通常只决定语义标签，不得覆盖单段布局；唯一例外是第 3 节经用户确认的全站摘要与关键词统一视觉组件。
- “其一/其二/其三”和普通正文即使同为 `paragraph`，也必须分别按 `layout` 渲染。
- CSS Module 只提供通用外壳；不使用 `!important` 覆盖 DOCX 行距、缩进和间距。
- 不允许为所有正文统一设置 `2em`、统一段后或统一标题外边距。

## 8. 图片与图注

- 通过 DOCX relationship id 获取原始 media blob。
- 记录 `sourceMedia`、原像素宽高、SHA-256、输出路径与原图注。
- 页面使用原比例完整显示；禁止 `object-fit: cover`、裁切、旋转、重新配色或替换为缩略图。
- 图注必须与原文一致，并与对应图片绑定，不得与前后图交换。
- 列表封面使用原文图 1 时只影响列表卡片，不得从正文中删除或移动图 1。

## 9. 数据表

- 保留表题、行数、列数、单元格文本与顺序。
- 禁止转置、重排、合并文案、拆成卡片或增加原文没有的状态色。
- 桌面端按 1180px 内容网格展示。
- 移动端允许表格容器内横向滚动，但移动视觉不属于正式验收。
- 当前 V2 已验证 7×3、6×3、5×3、5×4、6×4 表格；更大表格需单独过边界样本。

## 10. 文章类型与语义结构

当前 block 类型：

- `title`：详情页唯一 h1 的原文。
- `subtitle`：标题区原始副标题。
- `deck`：摘要前继续出现的居中标题说明；与 title/subtitle 一同放在文章头部。
- `abstract`：以“摘要｜”等标签开头，或由独立“摘要”标签段落与紧随其后的摘要正文共同构成；后一种结构必须分别保存标签与正文。
- `keywords`：以“关键词｜”或“关键词：”开头。
- `heading`：原文章节标题，渲染为 h2。
- `paragraph`：其他正文，样式仍由单段 `layout` 决定。
- `closing`：以“行动建议｜”、“落地建议｜”或“落地原则｜”开头。
- `figure` / `table`：原图与数据表。

分类器只能依赖可证明的 DOCX 文本/直接格式；新文章出现不同标题规则时先停止，不得为单篇堆文件名特判。

段落文本以“摘要”“摘要：”或“摘要｜”开头时，摘要识别优先于“第 3 个非空段落作为副标题”的位置推断；该优先级是全局规则，禁止为具体文件名增加例外。

使用 Word `Heading` 样式的段落直接分类为 `heading`；“核心判断”这类短标题若以直接加粗和标题色表达，也按可证明文本角色分类，不依赖文件名。

段落内嵌图片必须从该 `w:p` 的 `r:embed` 提取；若后一个文本段落符合“图N｜”，将其作为该图图注并保留图注段落属性，不再单独渲染。

顶层无图片表格前若紧跟“表N｜”文本段落，将该文本与后续 table block 绑定，不重复渲染。

## 11. 列表标题、封面与发布回退

1. MasterGo 已明确该篇列表标题/封面时，使用对应设计证据。
2. 没有单篇 MasterGo 证据时：
   - `displayTitle = sourceTitle`，不改写。
   - 封面使用 DOCX 图 1，`object-fit: contain`，不裁切。
   - 无合格图 1 时停止列表发布，不使用通用占位图。
3. 列表卡片不得将“立即阅读”做成无路由的伪按钮。

## 12. 日期、作者与新增内容

- DOCX 和正式发布台账未提供日期时，`publishedAt = null`，页面和 Article JSON-LD 均不输出日期。
- 不从文件创建/修改时间推断发布日期。
- 不自行增加作者、FAQ、CTA、相关阅读、资料来源或效果数字。

## 13. SEO / GEO 门禁

每个正式路由必须同时满足 `docs/seo-geo-guidelines.md`：

- 独立且准确的 title 和 description。
- 自指 canonical，不继承首页 canonical。
- 唯一 h1，h2 层级与原章节一致。
- 正文存在于服务端 HTML。
- Article 和 BreadcrumbList JSON-LD 只描述可见、已确认事实。
- 正式 URL 进入 sitemap，并从研究院列表获得可抓取内链。
- 本地只能报告“SEO/GEO 已实现，待线上验证”。

## 14. 单篇强制产物

`design-baselines/<page>/` 至少包含：

- `scope.md`：原文路径、哈希、分类、slug、视口、公共资产和用户覆盖。
- `content-ledger.md`：原文 block 数量、首末句、文字数、图片和表格深比较。
- `visual-ledger.md`：段落属性类型、图片尺寸、表格行列和用户例外。
- `seo-geo-validation.md`：元数据、canonical、标题层级、Schema、sitemap 和内链。
- `final-validation.md`：内容、视觉、SEO 和工程结论。
- DOCX 原始渲染页或结构审计记录。
- 1440px 桌面详情页截图；列表发布时另保留列表卡片截图。

## 15. 内容验收

必须同时通过：

1. 当前 DOCX SHA-256 与登记值一致。
2. 重新提取的 block 数、类型和顺序与正式 JSON 一致。
3. 每个 block 的 `text` 与 `segments` 重建文本逐字符一致。
4. 渲染 DOM 文本与正式 JSON 一致。
5. 图片数量、原像素宽高和 SHA-256 一致。
6. 表格数量、行列和每个单元格逐字一致。

任一项失败，该篇不得进入列表和 sitemap。

## 16. 桌面视觉验收

正式视觉验收只使用 1440px 桌面视口，至少检查：

- Header、文章头部、正文为同一 1180px 网格。
- h1/副标题居中，摘要距标题区 40px，上方无横线。
- 为每种段落属性类型抽样计算字号、行高、缩进、段前段后、底纹和边框。
- 三篇样板的摘要和关键词计算样式分别与统一基线一致；标签颜色、字号、字重和正文颜色必须逐项核对。
- 行动/落地建议按各篇 DOCX 底纹与左边框渲染，并保留网页内边距。
- 所有图片完成加载，天然尺寸与原素材一致，显示比例不变。
- 所有表格行列完整。
- `document.documentElement.scrollWidth === document.documentElement.clientWidth`。
- `article.bottom === footer.top`，正文不侵入 Footer。

无相同字体环境时，不声称字体像素级 1:1；必须报告字体替代限制。

## 17. 工程与证据门禁

每篇最终执行：

```bash
pnpm lint
pnpm exec tsc --noEmit
pnpm build
git diff --check
pnpm mastergo:check <page-slug>
```

生产构建必须显示该 slug 的静态路由。工程通过只证明代码可交付，不代表内容或视觉已通过。

## 18. 三类代表样板与 Stop Rule

V2 批量发布前必须完成：

1. 复杂图表型：《Agent OS 三层架构》，已通过当前 V2 回归。
2. 多表格型：《AI 催收的合规工程》，已通过当前 V2 回归。
3. 长文、段落内多图与外置表题型：《企业知识资产化实战》，已通过当前 V2 回归。

三类代表样板现已全部通过，V2 达到批量准入条件；这只解除规则层面的 Stop Rule，不等于剩余文章已经转换或验收。后续任一样板或新文章发现分类错误、文字丢失、布局属性遗漏、图片错位或表格破坏，立即：

1. 撤回“V2 冻结”结论。
2. 修正通用提取/渲染规则，不为单文件增加特判。
3. 回归已发布的全部文章。
4. 三类代表样板重新通过后再继续。

## 19. 完成口径

- **内容还原通过**：DOCX 哈希、block、文字、图片和表格深比较全部通过。
- **桌面布局校准通过**：在已登记官网化例外下，DOCX 段落属性和内容块顺序完成桌面回归。
- **SEO/GEO 已实现，待线上验证**：本地元数据、Schema、sitemap 和内链通过。
- **V2 批量准入通过**：只有三类代表样板均通过时才可使用。

无单篇 MasterGo 正文对照时，禁止声称“逐段 MasterGo 1:1”；应分别报告 DOCX 内容还原、桌面布局校准和官网化例外。
