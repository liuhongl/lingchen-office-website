# 灵宸官网 SEO / GEO 实施规范

## 1. 目标与边界

本规范用于让官网内容更容易被搜索引擎和生成式答案系统发现、理解、核验与引用，同时保持页面已声明的视觉真源和内容真源不被擅自修改。

- **SEO**：保证页面可抓取、可索引、主题明确、链接关系正确，并具备准确的搜索结果元信息。
- **GEO**：在 SEO 基础上，把经确认的公司、产品、能力、场景和案例事实组织成机器可理解、可定位、可核验的内容。
- GEO 是持续测量工作，不承诺某个生成式引擎必然收录、引用或推荐。
- 不以关键词堆砌、隐藏文本、批量生成低质量页面或伪造引用换取曝光。

## 2. 事实来源

所有 SEO/GEO 内容按以下优先级取值：

1. 用户确认的公司法定信息、正式产品资料、客户授权案例和有效资质。
2. MasterGo 当前设计稿中的可见原文。
3. 官网已经确认且仍有效的公共信息。
4. 原型或历史文档只能作为待确认候选，不能直接作为事实发布。

模型不得自行补写产品能力、效果数字、客户名称、行业排名、资质、价格、发布日期或引用来源。无法确认时标记 `BLOCKED`。

## 3. 每页开工前必须建立 SEO/GEO 台账

每个可索引页面必须创建 `design-baselines/<page>/seo-geo-validation.md`，并在写页面代码前确认：

- 页面用途、目标受众和唯一主主题。
- 唯一 URL、canonical URL、是否允许索引。
- 唯一 `title` 和 `description`，且准确概括页面真实内容。
- 页面唯一 `h1` 及合理的 `h2` / `h3` 层级。
- 核心实体及其正式名称、别名、实体类型和事实证据。
- 页面适用的结构化数据类型；没有匹配类型时不强行添加。
- 页面需要进入的 sitemap、站内导航和上下文链接。
- 内容负责人、事实审核人和最后复核日期。

## 4. 页面实现规则

### 4.1 元数据与 URL

- 每个可索引路由必须提供独立 `title`、`description` 和指向自身正式 URL 的 canonical。
- Open Graph 的标题、描述、URL 和图片必须与页面内容一致。
- URL 使用稳定、可读的英文小写路径；发布后不随意变更。确需变更时同步处理重定向、canonical 和 sitemap。
- 禁止多个不同页面都继承首页 canonical。
- `robots`、canonical 与 sitemap 的索引意图必须一致。

### 4.2 语义结构与可访问内容

- 使用 `header`、`nav`、`main`、`section`、`article`、`footer` 等符合含义的元素，不用无意义 `div` 取代全部结构。
- 每页只保留一个表达页面主主题的 `h1`；标题层级不得仅为视觉字号服务。
- 关键公司、产品、能力、案例和联系信息必须存在于服务端输出 HTML，不得只存在于图片、Canvas、CSS 伪元素或用户操作后的客户端状态。
- 图像必须有准确的 `alt`；纯装饰图像使用空 `alt`。图标名称不能冒充业务事实。
- 链接文字说明目标内容，避免大量使用“点击这里”“了解更多”等脱离上下文的文案。

### 4.3 GEO 内容组织

- 首屏或页面前部应能明确回答：主体是谁、提供什么、面向谁、解决什么问题。
- 产品页应优先形成可独立理解的事实单元：产品定义、适用对象、输入、处理过程、输出、边界条件和证据。
- 案例与指标必须同时给出适用范围、统计口径、时间范围和来源；缺一项不得作为确定性成果发布。
- 专业缩写首次出现时给出正式全称；同一实体跨页面保持名称一致。
- 对容易混淆的产品和概念，应明确差异、依赖关系与不适用场景。
- FAQ 只收录真实用户问题和已审核答案；不得为了 Schema 或关键词凭空生成问答。
- 内容更新时间必须真实，禁止只为制造新鲜度修改日期。

### 4.4 结构化数据

- 全站可以使用经核验的 `Organization`；页面按真实内容选择 `WebPage`、`Article`、`BreadcrumbList` 等类型。
- JSON-LD 中的信息必须在页面可见内容或正式事实资料中得到支持。
- 不添加与页面类型不符、只有营销用途或缺少必填属性的 Schema。
- 结构化数据修改后必须通过 Schema.org/Google 对应验证工具检查，并人工确认实体关系。

### 4.5 抓取、索引与站内关系

- 新的正式页面加入 `sitemap.xml`；草稿、测试页、重复页或不应公开页面不得误入 sitemap。
- `robots.txt` 不得意外阻止正式页面及其必要资源。
- 页面必须至少从一个可抓取的站内页面获得语义明确的链接，避免孤岛页面。
- 状态码、重定向、canonical、语言声明和最终 URL 必须一致。
- 不专门为不同搜索或生成式爬虫返回不同事实内容。

## 5. 与内容迁移和视觉还原的关系

- 页面 `scope.md` 声明的内容真源决定可见文案，视觉真源决定可见样式；SEO/GEO 决定语义标签、元数据、结构化数据和可抓取关系。
- SEO/GEO 优化不得擅自改写、扩写或隐藏添加内容真源文案。
- 不影响视觉的语义标签和元数据可以直接实现。
- 如 SEO/GEO 需要新增可见解释、FAQ、作者、日期或事实模块，必须先取得用户确认并回到 MasterGo 建立设计基线。
- “内容完整迁移通过”“视觉校准通过”和“SEO/GEO 通过”是三个独立结论，任何一项不能替代另一项。

## 6. 验收门禁

页面交付前至少验证：

1. 服务端 HTML 中存在正确的 `title`、description、canonical、唯一 `h1` 和主体内容。
2. canonical 指向当前正式页面，不错误继承首页地址。
3. robots 与 sitemap 返回成功，且页面收录意图一致。
4. JSON-LD 可解析、类型适配、字段有事实依据。
5. 内链可达，没有孤岛页和无意义链接文字。
6. 图片替代文本、标题层级和语言声明正确。
7. 台账中的每个实体和数字均有来源，没有模型推断事实。
8. 完成真实页面抓取检查；上线后再进行索引状态和生成式答案抽样监测。

只完成本地代码检查时，状态为“SEO/GEO 已实现，待线上验证”；只有线上可抓取、索引检查和约定的生成式引擎抽样完成后，才能报告“SEO/GEO 已上线验证”。

## 7. 禁止事项

- 隐藏文字、关键词堆砌、门页、伪造评论、伪造作者或伪造引用。
- 为迎合生成式引擎制造无依据结论或把推测写成事实。
- 将 JSON-LD 当作补充页面不存在内容的隐藏渠道。
- 把 `llms.txt` 或任何单一文件当作 GEO 收录保证；如未来采用，必须单独评估平台支持和维护成本。
- 用一次查询结果证明 GEO 成功；生成式答案具有波动性，必须保留日期、地区、查询表达、引擎和重复测试记录。

## 8. 度量与记录

SEO 与 GEO 分开记录：

- SEO：有效索引页、抓取错误、品牌/非品牌查询展现与点击、页面体验、结构化数据错误。
- GEO：按固定问题集记录品牌是否出现、事实是否正确、是否引用本站、引用页面、答案位置与错误类型。
- GEO 抽样必须使用多种等价问法并重复测试；只报告观察结果，不把相关性写成因果关系。
- 发布前建立基线，发布后按约定周期复测；查询集和原始结果应归档，不能只保留汇总百分比。
